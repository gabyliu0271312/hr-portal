# 绩效管理模块总体方案

## 1. 核心原则

### 1.1 绩效管理是独立业务应用

绩效管理模块不是 HR Portal 中的普通菜单页，而是一个相对独立的大系统。

第一期可以建设在现有 `hr-portal` 项目内，但需要保持清晰边界：

- 独立前端布局
- 独立后端模块
- 独立权限体系
- 独立数据模型
- 独立绩效流程配置
- 可被 HR Portal 入口访问，也可作为飞书独立应用访问

### 1.2 与现有 HR Portal 的关系：入口打通，内部独立

现有 HR Portal 只负责入口级权限控制：

- 谁可以进入绩效管理应用
- 谁可以进入绩效后台设置

绩效系统内部的角色、流程、数据范围、节点处理人、评价权限、申诉权限等，全部由绩效管理模块独立判断。

建议在现有 HR Portal 权限体系中增加入口权限：

- `performance.app`：允许进入绩效管理
- `performance.admin`：允许进入绩效后台

### 1.3 认证可复用，绩效人员不强依赖现有用户表

从 HR Portal 进入绩效管理时，可以复用现有登录态。

从飞书工作台独立进入时，走飞书 SSO。飞书身份优先通过手机号或邮箱匹配绩效人员，后续如员工实时花名册补充飞书用户 ID，则优先使用飞书用户 ID。

绩效人员主数据来自现有系统的员工实时花名册，不强制来自 HR Portal 的 `users` 表。

### 1.4 权限分三层

绩效权限不应简单复用现有菜单权限体系。推荐分为三层：

1. HR Portal 入口权限
   控制用户能否进入绩效管理、能否进入绩效后台。

2. 绩效系统配置权限
   控制用户能否配置周期、流程、等级、模板、项目规则、强制分布、申诉规则等。

3. 绩效流程身份权限
   系统根据员工花名册、组织关系、项目关系、流程节点、绩效周期自动计算用户在具体事项中的权限。

典型流程身份包括：

- 本人
- 直属上级
- 项目负责人
- 部门/组织校准人
- 公司级校准人
- 申诉处理人

### 1.5 绩效流程采用时间节点驱动

绩效管理不是传统审批流驱动，而是时间节点驱动。

节点可以重合、并行开放。系统判断：

- 当前时间是否在节点操作窗口内
- 当前时间是否超过最晚提交时间
- 当前用户是否是节点处理人
- 当前记录是否已经提交
- 是否允许逾期补提交
- 是否允许修改最终分数或等级

### 1.6 流程可配置，周期启动后快照固化

后台配置流程模板。每个绩效周期选择一个流程模板。

周期启动后，需要将以下内容固化为周期快照：

- 流程节点
- 节点时间窗口
- 节点最晚提交时间
- 节点权重
- 绩效等级体系
- 强制分布规则
- 人员范围
- 处理人规则

后续修改模板只影响新周期，不影响已经启动的周期。

### 1.7 配置层统一，底层数据分开

工作内容总结、员工自评、上级评价、项目评价、校准、申诉都属于绩效流程配置中的节点。

但底层数据需要分开存储，便于：

- 独立提交
- 独立统计进度
- 独立设置时间窗口
- 独立审计
- 独立参与最终分数计算

例如工作内容总结和员工自评可以配置为同一时间段开放，但底层仍然分开存储、分开提交。

### 1.8 全过程必须可追溯

绩效结果涉及敏感人事决策，必须记录完整轨迹：

- 谁提交了什么内容
- 谁给了什么评分
- 谁调整了最终等级或分数
- 从什么值调整到什么值
- 调整发生在哪个节点
- 是否填写原因
- 申诉最终反馈是什么

员工只能看到允许公开的内容，HR、绩效管理员、相关评价人根据权限看到不同范围的过程信息。

### 1.9 在 HR Portal 中作为一级应用入口

绩效管理应作为 HR Portal 的顶部一级应用入口，而不是放在“提效工具”或“系统设置”下面。

HR Portal 是应用门户和入口授权中心。绩效管理进入后使用自己的应用布局、顶部 Tab、左侧菜单和后台设置。

该原则与 HR Portal 的应用接入模型保持一致：

```text
specs/001-hr-permission-portal/application-access-model.md
```

## 2. 顶部信息架构

绩效管理前台包含三个顶部 Tab：

- 工作台
- 绩效评估
- 项目管理

每个 Tab 下使用左侧菜单，保持与当前 HR Portal 类似的操作习惯。

建议前端路由：

```text
/performance
/performance/workbench
/performance/review
/performance/projects
/performance/settings
```

建议新增独立前端布局：

```text
frontend/src/layouts/PerformanceLayout.vue
```

## 3. 推荐菜单结构

### 工作台

- 我的待办
- 我的绩效
- 团队进度
- 申诉处理

### 绩效评估

- 当前周期
- 工作内容总结
- 员工自评
- 上级评价
- 项目评价
- 校准管理
- 结果查看
- 申诉反馈

### 项目管理

- 项目列表
- 项目成员
- 项目权重
- 项目评价
- 项目进度

### 绩效设置

该菜单仅对具备绩效后台权限的用户展示。

- 周期设置
- 流程模板
- 评价模板
- 绩效等级
- 强制分布
- 项目规则
- 申诉规则
- 人员同步
- 权限配置

### 3.1 角色与主入口

绩效系统的页面入口和主要操作按流程身份组织，不应只按后台菜单组织：

| 角色 | 主要入口 | 核心操作 |
|---|---|---|
| 员工 | 工作台、绩效评估 | 查看待办、填写工作总结、自评、查看结果、提交申诉 |
| 直属上级 | 工作台、绩效评估 | 查看待评价人员、阅读相关材料、提交上级评价 |
| 项目负责人 | 项目管理、绩效评估 | 管理绩效项目成员、查看项目权重、提交项目评价 |
| 部门/组织校准人 | 工作台、绩效评估 | 查看组织范围内初算结果、调整等级或分数、填写校准原因 |
| 公司级校准人 | 工作台、绩效评估 | 查看公司范围内结果、完成公司级校准 |
| 绩效管理员 | 绩效设置、工作台 | 创建周期、配置模板和规则、启动周期、查看进度、发布结果、处理申诉 |

HR Portal 只负责应用级入口；用户进入绩效系统后，页面和操作权限由绩效角色、周期人员快照、项目关系和流程节点身份共同决定。

### 3.2 角色主流程

员工主流程：

```text
工作台
-> 我的待办
-> 工作内容总结
-> 员工自评
-> 查看提交状态
-> 结果发布后查看最终结果
-> 必要时提交申诉
```

评价人主流程：

```text
工作台
-> 待评价任务
-> 查看被评价人的允许可见内容
-> 填写并提交评价
-> 查看任务完成状态
```

绩效管理员主流程：

```text
绩效设置
-> 创建或编辑周期
-> 选择流程/评价模板
-> 配置参与人员和规则
-> 启动周期
-> 查看任务与评价进度
-> 发布结果
-> 处理申诉和审计事项
```

### 3.3 第一条最小业务闭环

第一阶段优先验证以下纵向链路，而不是先完成所有后台配置页面的像素级还原：

```text
管理员创建周期
-> 选择模板并配置参与人员
-> 启动周期并固化人员/流程快照
-> 为员工生成工作总结和自评任务
-> 员工保存并提交工作总结
-> 员工保存并提交自评
-> 直属上级提交评价
-> 系统生成初算结果
-> 管理员发布结果
-> 员工查看最终结果
```

每个纵向切片都应同时包含必要的后端能力、必要的后台配置、用户端页面、权限判断、测试和真实读取/重开验证。

### 3.4 配置层与运行层的交互边界

后台配置不是运行时任务本身，二者通过周期启动快照连接：

```text
管理员配置模板
-> 周期选择模板
-> 周期启动
-> 固化周期人员、流程、规则和处理人快照
-> 根据快照生成节点任务
-> 员工和评价人按任务状态操作
```

模板修改只影响新周期；已启动周期的人员、组织关系、节点规则、评价权限和任务依据不得被实时数据静默改写。

对于截图未覆盖的业务行为，不能由前端参考图自行推断；对于尚未确认的角色、权限、算法、状态或可见范围，应先记录为待确认事项。

## 4. 核心流程

绩效流程不是固定流程，而是由后台配置节点。

第一期建议支持以下节点类型：

- 工作内容总结
- 员工自评
- 上级评价
- 项目评价
- 部门/组织校准
- 公司级校准
- 结果修正/复核，可选
- 结果发布
- 申诉处理

其中：

- 工作内容总结和员工自评是独立节点，可配置为时间重合，也可配置为不同时间。
- 校准节点可以直接修改最终等级或分数。
- 是否必须填写校准原因由后台配置。
- 结果修正/复核节点不是固定节点，如配置则允许修改最终等级或分数，否则没有业务价值。
- 结果发布后员工可以查看最终绩效结果。
- 每个周期每人最多申诉一次。
- 申诉处理后必须反馈最终等级、最终分数和反馈说明。

## 5. 结果链路

绩效结果建议按以下链路生成：

```text
评价初算结果
-> 部门/组织校准结果
-> 公司级校准结果
-> 可选结果修正/复核结果
-> 发布结果
-> 申诉处理结果
```

如无申诉，最终结果为发布结果。

如有申诉，最终结果以申诉处理反馈的等级和分数为准。

## 6. 员工可见范围

员工最终结果页可以看到：

- 最终等级
- 最终分数
- 工作内容总结
- 自评内容
- 上级评价内容
- 申诉反馈说明，如有

员工不可见：

- 校准说明
- 校准调整过程
- 强制分布调整说明
- 内部复核说明

## 8. 视觉风格原则

绩效管理可以拥有独立路由、独立布局、独立权限、独立流程和独立后台，但不应拥有割裂的视觉体系。

绩效管理应继承 HR Portal 的统一设计系统：

```text
hr-portal/frontend/docs/design-system.md
```

平台级主色使用飞书蓝：

```text
#3370ff
```

绩效管理允许增加业务语义色，例如：

- 绩效等级颜色
- 流程节点状态颜色
- 申诉状态颜色
- 项目评价图表颜色

但不建议单独定义另一套主色、按钮、卡片、表格、菜单和弹窗风格。

目标体验是：

```text
用户感觉仍在同一个 HR Portal 平台内，只是进入了一个更完整的绩效应用。
```
