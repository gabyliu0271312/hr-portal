## 2. 身份管理页面（T06，2026-10-28 最新调整）

### 2.1 入口与权限

- 入口：**系统设置 → 权限管理 → 身份管理**；独立于角色配置。
- 页面标题：**身份管理**；菜单归属 `system.auth`，拟路由 `/system/identity-management`，注册 code 与 meta.menuCode 同为 `system.identity_management`。
- 仅内置 admin 可见和可访问；非 admin 超级管理员也不能通过菜单、路由或直接 API 获得访问权。
- 页面管理权是内置账号策略，不在角色矩阵中提供可授予的“身份管理”权限；角色配置中的“绩效用户切换”是另一项使用授权。

### 2.2 四列表格

| 系统名称 | 描述 | 状态 | 操作 |
| --- | --- | --- | --- |
| 绩效系统 | 允许已授权用户切换为绩效员工，按员工实际业务权限测试 | 已停用 / 已启用 | 停用时为“启用”，启用时为“停用” |

- 本期只有上述一行，不增加其他系统占位行，也不提供新增/编辑/删除系统功能。
- 状态只说明其他用户切换能力是否开放；页面固定说明“admin 始终保留切换资格”，避免把已停用误认为 admin 也不可用。
- 不再以行内 Switch 或“打开开关”列操作；启停按钮操作成功后才刷新状态/按钮文案，处理中禁用重复点击，失败不伪显示成功。
- 消息测试设置保留在表格下方的独立配置区域，明确作用于绩效系统；不挤进四列表格，也不额外添加未要求的行操作。

### 2.3 启用

1. 停用状态行显示“启用”。
2. 点击后调用真实 API；成功变为“已启用”，按钮变为“停用”。
3. 提示“已启用。其他用户仍需到角色配置重新授予身份切换权限。”
4. 不自动授予任何角色、不恢复历史勾选和旧会话。

### 2.4 停用并清空授权

- 已启用状态行显示“停用”。点击打开确认框，标题为“停用并清空其他用户的身份切换授权？”。
- 明确清空所有角色这一项授权，包括超级管理员角色；非 admin 已有会话失效，再启用需重配。
- admin 资格和会话不因公共停用失效；不删除账号、员工、其他权限或审计，也不回滚已完成业务。
- 按钮：取消 / 停用并清空；发送 expected_revision、request_id、confirm_clear。
- 成功后显示“已停用”，行操作变“启用”；反馈真实清空角色数及撤销会话数。
- 失败保持服务端已知状态；409 提示刷新后重新确认，不能自动覆盖并发配置。

### 2.5 刷新与重启

刷新和服务重启后回读真实启停状态；不保留关闭前授权备份用于恢复。角色配置页独立读取当前资格状态与 generation，旧页面不能写回已撤销授权。

## 3. 角色配置矩阵（T06）

- 位置：现有角色编辑 → 绩效管理 → 应用权限，名称为 **绩效用户切换**。
- 权限码提案：`performance.identity_switch`；只使用 V/可使用，非适用的 C/U/D/E 不展示为可授予开关管理权。
- 公共开关关闭：勾选项禁用并显示“开关已关闭，无法授予”；不能给 admin 勾选一个假权限来实现其内置特权。
- 公共开关开启：具备既有角色维护权的操作者可显式勾选、保存；不得因“全选全部菜单”或超级管理员自动补权隐式带入此项。
- admin 也可以为其他角色配置，但其自身资格不来自任何角色。
- 保存携带读取时的 identity_switch_generation；旧表单在关闭/重开后保存，明确提示“身份切换授权已清空，请刷新后重新配置”，不自动重试写回旧值。
- 修改其他菜单、角色描述等既有功能保持行为；不能因关闭开关就把用户整份角色配置静默丢弃。
- 前端控制不能代替后端版本/权限校验；自动化覆盖直接构造旧 payload。

## 4. 绩效右上角“切换用户”（T07）

### 4.1 未切换状态

- 正常保持现有用户显示和后台管理/退出登录。
- 后端 can_switch=true 时显示“切换用户”；admin 在公共开关关闭时仍显示。
- 无资格时不显示入口；手动调用人员查询/会话 API 仍拒绝。
- 打开弹窗不视为已切换，不先渲染目标数据。

### 4.2 人员选择弹窗

- 标题：**切换绩效用户**。
- 复用现有人员搜索选择方式，单选；人员数据来自员工主数据及获批准的历史参与者范围，不能从 Portal users 截断名单。
- 搜索条件：姓名或员工编号；结果显示姓名、员工编号、必要的组织标签。重名必须可区分，不暴露手机号、邮箱、薪酬等无关信息。
- 提示：**将按所选员工的实际绩效权限访问，不会为其创建 Portal 账号或额外授予角色。**
- 2026-10-28 已确认开发与生产支持真实操作，显示“操作将按目标员工权限影响业务数据”；同时明确切换操作的通知拦截范围。不得通过弹窗勾选恢复发送消息；原业务接收方始终禁投；默认仅记录，admin 开放受控测试投递后，每次一条独立汇总，样式验证另发一条样例。
- 按钮：取消 / 确认切换；未选人或查询/提交中不可确认。
- 空数据：没有匹配员工；允许修改关键词，不提示“先去用户管理开户”。
- 来源失败：显示加载失败及重试；不回退成管理员全量名单，不把故障当无人。
- 确认只提交 employee_no、expected_generation、request_id，不由客户端指定 admin/operator 或提升模式。

### 4.3 成功切换

1. 清理本页旧会话/数据；若从另一目标切换，先幂等退出旧会话，再创建新会话。创建失败保留明确的本人状态，不伪装仍是旧目标。
2. 保留 Portal 原始登录，切换凭证只驻当前页内存，不写 localStorage、URL、日志或其他页面共享存储。
3. 重取目标访问上下文、导航和功能权限，重置当前项目、列表、人数、统计和表单缓存，取消在途请求。
4. 重新加载目标工作台；若当前路由/项目不在目标可见范围，回工作台，不保留操作者后台页面。
5. 迟到的旧请求必须按会话/身份版本丢弃；不能出现先显示甲的数据再被乙覆盖的短暂泄漏。

### 4.4 持续身份提示

整个切换期间持续显示：

> 正在以「姓名 · 员工编号」身份测试｜实际操作者：XXX｜当前模式：XXX｜恢复本人

- 姓名/编号可截断但可查看完整值，窄屏不能挤掉恢复入口。
- 右上角显示目标员工并保留明确“切换中”标识，不只换头像或姓名。
- 当前可继续切换及恢复的控制资格取原始操作者；业务菜单、字段、按钮取目标员工，不能混用。
- admin 关闭公共开关后，其切换状态仍保留；非 admin 会话按下节失效。

## 5. 恢复、失效与跨页面隔离（T07）

### 5.1 恢复本人

点击恢复，幂等退出当前切换会话、清理凭证和目标缓存，重新加载原始本人上下文。原会话已经失效也必须允许本地清理；网络故障要明确提示退出未获服务端确认，不能保留可误用的目标数据。原始操作者未登录则返回登录页。

### 5.2 关闭、撤权或到期

下一次请求收到对应失效错误后：

- 清理当前切换凭证、目标数据与在途请求，隐藏目标业务内容。
- 明确提示：**身份切换已失效，请恢复本人或重新申请授权。** 清理完成后保留原始操作者的切换资格，若开关和授权仍有效，用户可直接再次选择员工创建新会话，不要求刷新页面或重新激活功能。
- 禁止把失败请求用 admin 身份自动重试；否则可能误显示管理员全量数据或代为提交。
- 关闭已交付的数据不能追回，但页面后续使用和异步导出下载必须重新校验资格。
- 刷新页面默认恢复本人；不能从浏览器持久化中重新载入旧切换凭证。
- 页面重新获得焦点或从后台恢复可见时立即检查会话；相同会话的重叠心跳去重，不把网络/5xx 当成到期，服务端续期结果回写本页状态。
- 独立全屏填写工作区（工作总结/模板任务）与常规绩效布局复用相同的15秒心跳和恢复检查；不能因进入全屏页卸载主布局而停止续期。有效切换身份下返回/取消只回原入口并保留周期、项目、环节，不恢复本人；真实到期仍按服务端拒绝处理。回归证据见 CR-008-T01-F01。
- 旧会话心跳、旧身份上下文和旧切换资格请求迟到时不得覆盖新会话或新入口状态；组件卸载必须移除恢复监听和心跳定时器。

### 5.3 标签页与应用

- 标签 A 切换甲，标签 B 仍为真实操作者；不覆盖共享 Portal token。
- 页面内“恢复本人”只退出本页会话；Portal 的真正“退出登录”仍清原始登录，并使其关联切换请求不能继续使用。
- 离开绩效进入 Portal、绩效后台或其他应用，不携带目标员工身份；如打开新页，保持原始登录。
- 离开应用前提示并退出本页切换会话；若只是绩效前台内部导航，保留本页有效身份。绩效后台是否需要目标管理身份测试须 T01 明确，不默认把操作者后台权带入切换状态。
- 页面异常、网络错误不默默切回管理员显示；需明确恢复动作或可感知的状态变化。

## 8. 追加交互约束：可写与消息隔离（2026-10-28）

- 首轮不是只读预览。确认切换前和持续身份提示中明确：操作会改变业务数据。
- 用户已明确原业务接收人及业务群始终零投递；提示“原业务消息已拦截”，受控测试消息独立显示状态。前端不能自行发送、不提供任意恢复消息投递的入口。
- 保存/提交成功与消息状态分开反馈；业务成功、通知被策略拦截不得误显示为“消息发送成功”或“操作失败”。
- 正常员工通知和绩效全局通知配置不因有人切换身份而改变。异步发送/重试也要保留操作来源，不在恢复本人后补发。

## 9. 单样例与每次独立结果汇总（2026-10-28）

- admin 配置：默认仅记录；受控测试投递默认关闭，开放后配置经过核验的测试接收方。不提供恢复原业务收件人投递的选项。
- 每次测试均单独生成结果汇总。受控投递开启时发送 1 条汇总；若验证样式，再单独发送 1 条样例，合计最多 2 条，与原业务通知人数无关。仅记录模式生成两类预览但零外发。
- 批量启动示例：500 人逐条生成核验，只给合规测试接收方发送 1 条样例和 1 条汇总，不转发 500 条；分页、队列分片、重试不算新测试。
- 汇总包含环境、批次/业务对象、真实操作者、目标员工、计划人数、生成成功/失败/未完成、原接收方拦截数、样例投递状态、受权限保护的明细入口；生成成功不等于送达成功。
- 样例失败也可由独立汇总报告；汇总发送失败仍可页面查询，不误报整轮通过、不回退发原收件人。未知投递回执显示待核对，不盲目补发。
- 测试接收方若属于本批原接收范围（例如全员名单内的 admin），明确阻止外发并保留记录，不自动换成操作者本人；两类测试消息也必须遵守原接收方禁投。
- 样例/汇总标记测试与环境；链接和业务按钮不能让测试接收方冒充员工。关闭受控投递、撤权或退出切换后，原通知永不补发。
- T06/T07 蓝图、独立截图和组件测试必须覆盖以上状态；当前仅更新需求，不构成 UI 或投递实现完成证据。
