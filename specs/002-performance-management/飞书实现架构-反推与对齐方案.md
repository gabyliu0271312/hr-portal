# 飞书绩效模板「预览」实现架构：反推与对齐方案

> 抓取对象：`https://idreamsky.feishu.cn/perf/admin/templates/7703786341502307621/4`
> 抓取方式：CDP 真实浏览器（headed，持久化登录态）→ DOM attributes / React fiber / dva store / 网络接口 / 真实点击键盘
> 抓取资产：`rea-extract/out/impl-flow/`（`template-detail.json`、`behaviors.json`、`store-*.json`、`network.json`、`interaction.json`、`entity-model.md`、`placement-matrix.md`）

---

## 一、结论摘要

飞书的预览不是"照着填写页复刻一份只读 DOM"，而是**同一条渲染链路 + 一套声明式配置**：

```
归一化实体图（flow/stage/template/templateItem/entry/subEntry/subIndicator/subField）
        +
设置声明表（32 张 behavior 表，按 (flow, stage, template, templateItem, entry, subField) 定位）
        ↓
真实表单渲染器（PreviewViewportWrapper → Field → 真实控件）
        ↓
预览态只把「提交」置灰，其余控件全部是活的（富文本可输入、添加可增行）
```

三个直接可见的后果：

1. **同一份内容只存一次**，不同环节的差异由声明表按 `stage` 维度叠加，不复制内容。
2. **内容设置不是字段属性**，是独立的一张张"声明记录"，字段本身不知道自己是必填还是只读。
3. **预览与填写共用渲染器**，所以"预览里的填写逻辑与真实填写一致"是架构的自然结果，不需要单独保证。

## 二、飞书的四层架构

### 第 1 层：归一化实体图

接口 `/perf/api/review/v2/template_groups/{id}/detail` 返回 `entities` 表，实体之间只存 `{id, type, _type:'ref'}` 引用：

| 实体 | 数量 | 关键字段 | type 枚举 |
|---|---|---|---|
| `flow` | 1 | `stages[]`、`finalResult`、`scenes` | — |
| `stage` | 9 | `stageModel`、`type`、`readTemplates`、`writeTemplates`、`modifyTemplates`、`referenceTemplates`、`stageConfigs` | `keywork_and_invitation` / `leader_review` / `adjust_review` / `view_result` / `appeal` / `my_business_team` |
| `template` | 33 | `templateItems[]`、**`ref`** | `template` |
| `templateItem` | 16 | `name`、`description`、`entries[]` | `evaluatedContent` / `question` / `unit` / `prompt` |
| `entry` | 16 | `subEntries[]`、`useSubIndicator` | `multiple_texts` / `text` / `indicator` |
| `subEntry` | 1 | `min` / `max` / `decimal` / `scoreOptions` / `subIndicators[]` | `score_admin_weight` |
| `subIndicator` | 1 | `label`、`weight`、`score`、`subFields[]` | — |
| `subField` | 1 | `name`、`description`、`type` | `text` |

两个要点：

- **`template.ref` 是复用机制**：`sdk-atAICU1yZFR_...`（自评环节的工作总结）`templateItems: []` + `ref: sdk-2PaBQqC7C_...`，即"自评引用填写工作总结的那份模板"，不复制条目。
- **`stageModel` 决定右栏渲染哪套表单**：`goal_setting`（目标/总结）、`review`（评估）、`adjust_review`（校准）、`view_result`（只读结果）、`appeal`（复议）、`virtual`（我的团队）。这就是"其他节点"的分类依据。

### 第 2 层：设置声明表（内容设置的真身）

dva store 顶层 **47 个 `sdk/behavior/*` model**，其中 32 张有数据。每张表一行 = 一条声明，用四元组/五元组定位：

| 表 | 记录数 | 字段 | 语义 |
|---|---|---|---|
| `entrySetting` | 84 | `flow, stage, template, templateItem, entry, subIndicator, subField, viewType, required` | **可编辑/隐藏 + 必填**，`viewType: edit \| hide` |
| `permission` | 946 | `flow, stage, template, templateItem, entry, subIndicator, subField, rating, mode` | **权限**，`mode: read \| write \| modify` |
| `allowMultiple` | 1 | `flow, template, templateItem` | **允许添加多条**，独立一行声明 |
| `hidden` | 1 | `flow, template, entry` | 整条 entry 隐藏 |
| `okrRatingSetting` | 6 | `objectiveViewType, objectiveRequired, keyResultViewType, keyResultRequired, need_okr_detail_score` | OKR 参考内容的读写与必填 |

其余 27 张（`allowUnknown`、`notAllowManual`、`hideRating`、`calculationRule`、`coefficientViewType`、`orgSetting`、`permission` 之外的能力开关等）当前为空，但**结构是同一套**——需要哪个设置，就新增一张表，而不是给字段加属性。

**同一实体在不同环节的差异，就是查表结果不同**（实测自 `placement-matrix.md`）：

| 环节 | 模板项 | permission.mode | entrySetting.viewType |
|---|---|---|---|
| 填写工作总结 | 工作总结 | `write` | `edit` |
| 上级评估 | 工作总结 | `read` | `edit` |
| 我的团队 | 工作总结 | `read` | — |
| 自评 | 价值贡献 / 投入度 / 价值观 | `write` | `edit` |
| 360°反馈 | 综合评级 | `read` | `edit` |

同一条「工作总结」记录，被 6 个环节引用，靠表决定谁能写、谁只能读。

### 第 3 层：渲染链路

React fiber 的 props 直接暴露了结构：

```
PreviewViewportWrapper{children}
  └ Z{writeTemplateIds, expanded}
      └ null{leftComp, rightComp}          ← 左/中/右是插槽，不是写死的三栏
          └ tt{flowId}
              └ … → Field                  ← 表单字段渲染器
```

- `readTemplateIds` / `writeTemplateIds`：**参考内容按读模板拉取，填写内容按写模板渲染**。
- `PreviewViewportWrapper` 内部有 `scroll-container / inner-scroll-wrap / inner-scroll / footer`，`footer` 里是 `提交(disabled) / 取消`——这就是"预览"，只禁用了提交。
- DOM class 指纹：`ud__*` = 飞书 UD 组件库；`next-remix-rich-text-editor*` + `editor-kit-*` + `data-slate-editor` = **基于 Slate 的 editor-kit 富文本**。

### 第 4 层：交互与状态

真实交互实测（`probe-interaction.js`，真实 `page.click` + `page.keyboard`）：

| 操作 | 结果 |
|---|---|
| 点击编辑器 | `document.activeElement` = `div[contenteditable=true]`，**焦点真实进入** |
| 键盘输入 | 成功写入，`ace-line` 行容器承接文本，Ctrl+Z 可撤销 |
| 点击「添加」 | 编辑器实例 **1 → 2**，新块标题自动变「重点工作 2」，右上角出现删除图标 |
| 工具栏 | 24 个按钮全部 enabled |

**教训**：用 `dispatchEvent(new MouseEvent(...))` 测不出聚焦，浏览器只在真实指针事件时执行默认聚焦行为——第一版探针因此误判"预览不可编辑"。

预览态的位置只存两个 id：

```js
templatePreview = { currentFlowId, currentStageId, currentTemplateType, currentSelectedLevelId }
```

数据本体全在实体表里，所以切换环节时只是换 `currentStageId`，右栏重新查表渲染——**这就是"切节点分割线/内容稳定"的根因**：布局由外层决定，内容只是数据替换。

## 三、与当前实现的逐项对照

| 维度 | 飞书 | 我们（现状） | 差距性质 |
|---|---|---|---|
| 数据组织 | 归一化实体 + `{id,type,_type:'ref'}` 引用 | `node.content[]` 内嵌完整内容，`item.settings{}` 内嵌设置 | 结构不同 |
| 模板复用 | `template.ref` 指向另一模板 | `content_slot` 复制一份内容到各节点 | 结构不同 |
| 环节差异 | `permission` / `entrySetting` 按 stage 声明 | 每个节点的 `content[]` 各存一份，差异体现在数据本身 | 语义不同 |
| 允许添加 | `allowMultiple` 独立表 + `entry.type=multiple_texts` | `item.settings.allowMultiple` / `content.settings.allowMultiple` 布尔值 | 语义相同，位置不同 |
| 只读/隐藏 | `entrySetting.viewType: edit\|hide` + `permission.mode=read` | `item.settings.mode: fill\|hidden\|view` | 我们把 read 与 edit/hide 混在一个枚举里 |
| 必填 | `entrySetting.required`（可细到 subField/subIndicator） | `item.settings.required`（只到 item 级） | 粒度更粗 |
| placeholder | `subField.description` 直接作为 `data-placeholder` → `::before` | `item.hint` 硬编码"请输入内容" | 数据来源不同 |
| 预览渲染 | 真实表单渲染器 `Field` | `PerformanceContentRenderer` 只读复刻 | **路线不同** |
| 富文本 | Slate 真实编辑器，`contenteditable=true` | `PerformanceRichTextBox readonly` + 纯 `div` | 无编辑能力 |
| 多实例 | 真实数组，加行/删行/序号 | 固定一组，「添加」按钮无事件 | 无状态层 |
| 三栏 | `leftComp/rightComp` 插槽按 flowId 注入 | `PerformanceTemplatePreviewStep` 内写死三栏 | 可接受，但耦合 |

## 四、对齐方案

完全照搬飞书需要后端改协议（归一化 + 47 张表），代价过大。**前端可以先在语义上对齐，后端协议不动**：引入一个"设置解析器"，把现有内嵌 settings 投影成飞书式的四元组查询视图，再让预览复用一个渲染器。

### 阶段 1：设置解析层（✅ 已交付 `performanceContentSettingsResolver.ts`）

> 落地（2026-11-04）：`resolveFieldSettings(ctx)` 已按下表规则实现，新增
> `performanceContentSettingsResolver.spec.ts`（11 用例）。只读判定同时覆盖三种来源：
> ① 节点类型只读（result_view / reviewer_360_invite / result_reconsideration）；
> ② `content.content_slot === 'view'`（参考内容查看态）；③ 条目 `mode === 'view'` 或校准 `allowModify === false`。
> 预览与内容设置今后都调这一个函数取渲染指令。

把"从嵌套对象里各取各的"改成"统一查一次，得到一份渲染指令"：

```ts
export type ResolvedFieldSettings = {
  viewType: 'edit' | 'hide'          // 对应飞书 entrySetting.viewType
  permission: 'read' | 'write'        // 对应 permission.mode
  required: boolean
  allowMultiple: boolean
  hideName: boolean
  hideDescription: boolean
  placeholder: string                 // 来自 hint / description，对齐 subField.description
}

// 输入：(node, content, item) —— 现有数据形状
// 输出：ResolvedFieldSettings —— 渲染器与预览共同消费
export function resolveFieldSettings(ctx: {
  node: PerformanceWorkflowNode
  content: PerformanceTemplateContent
  item: PerformanceTemplateContentItem
}): ResolvedFieldSettings
```

关键规则（按飞书语义归并现有字段）：

| 现有字段 | 映射到 | 说明 |
|---|---|---|
| `item.settings.mode === 'hidden'` | `viewType: 'hide'` | 隐藏优先 |
| `item.settings.mode === 'view'` | `viewType: 'edit'` + `permission: 'read'` | 飞书没有 view 态，只读=可渲染但不可写 |
| `item.settings.mode === 'fill'` 或缺省 | `edit` + `write` | |
| 节点只读（结果/校准只读节点） | `permission: 'read'` | 由 `node_type` 派生，不再靠复制内容 |
| `content.settings.allowMultiple \|\| item.settings.allowMultiple` | `allowMultiple` | 归并到一处 |
| `item.required ?? contact.settings.required` | `required` | |
| `item.hint \|\| content.description` | `placeholder` | 对齐 `subField.description` |

**收益**：预览与填写两个入口都调这一个函数，设置的读法只有一处，避免两套解释继续漂移。

### 阶段 2：渲染统一（✅ 已交付 `performanceContentToSections.ts`）

> 落地（2026-11-04）：`contentToSections(node, contents)` 已实现（含 `performanceContentToSections.spec.ts` 9 用例）。
> 预览右栏「配置填写内容」已改走 `PerformanceTemplateRenderer(mode="edit")` 复用真实填写链路：
> 富文本是真编辑器（contenteditable=true、可聚焦可输入、工具栏可用）、「添加」真实增行并带序号与删除图标、
> placeholder 取条目 hint → 内容 description（对齐 subField.description）。查看/校准/说明块仍走只读复刻。
> 渲染器新增 `showHeader`（预览由外层渲染 REA 块标题）与 `placeholderFallback`（预览传空串，避免出现填写页的「提示」兜底）两个透传。

新增适配层 `performanceContentToSections.ts`，把配置态 `content[]` 投影成填写态 `PerformanceTemplateSection[]`：

```ts
export function contentToSections(
  node: PerformanceWorkflowNode,
  contents: PerformanceTemplateContent[],
): PerformanceTemplateSection[]
```

映射规则（与飞书实体链一一对应）：

| 飞书 | 我们 | 说明 |
|---|---|---|
| `templateItem.type=evaluatedContent` | `content.type='work_summary'` | 多行富文本，`entry.type=multiple_texts` |
| `templateItem.type=question` | `content.type='custom'` + `item.questionType` | 评级题 / 单选 / 标签 |
| `templateItem.type=unit` | `content.type='rating'` | 综合评级 |
| `templateItem.type=prompt` | `content.type='prompt'` | 说明块，不占填写位 |
| `entry.type=multiple_texts` | `section.allow_multiple=true` | 允许添加多条 |
| `subField.description` | `field.placeholder` | 编辑器占位文案 |

然后预览右栏直接渲染：

```vue
<PerformanceTemplateRenderer
  mode="edit"
  :sections="sections"
  :answers="answers"
  :editable="true"
  :readonly-fields="readonlyFieldIds"
/>
```

复用真实链路的四类控件（富文本 / 评级 / 标签 / 单选）与实例增删，删除 `PerformanceContentRenderer` 里的只读复刻分支。

### 阶段 3：交互与像素细节

阶段 2 之后，以下问题应当**自动消失**（因为不再是复刻）：

- 富文本可输入、有焦点、工具栏可用
- 「添加」真实增行、带序号、带删除图标
- 四种填写内容的行为与填写页一致

仍需单独补的像素细节（本次新增实测值）：

| 项 | 实测值 |
|---|---|
| 编辑区 padding | `6px 8px 0`，文字 14px/22px `#1F2329` |
| 行容器 `ace-line` | 高 24、line-height 24、空行用零宽字符撑高 |
| placeholder | `::before`，色 `#8F959E`，`white-space: pre-wrap`，`absolute; top:6px; left:8px`，文案取 `subField.description` |
| 实例标题 | `${name} ${index}`，如「重点工作 1」「重点工作 2」 |
| 删除图标 | 每实例右上角 |
| 外框 | 631.3×143.3、radius 6、1px `#d0d3d6`、toolbar 36 |
