# ADR-002：业务骨干优先与分级 UI 还原策略

- 状态：已确认
- 日期：2026-09-04
- 范围：绩效管理后续规格、前后端开发、UI 采集与验收、AI 协作
- 决策类型：长期开发策略

## 1. 背景

绩效系统当前同时推进以下三类高复杂度工作：

1. 参考外部系统进行前端视觉和交互还原；
2. 根据本项目业务目标自行设计绩效领域、权限、流程、数据与 API；
3. 实现高密度的管理员配置页面及其大量状态分支。

现有工作已经建立了绩效独立应用入口、权限基础、设计 Token、UI 蓝图、采集契约、组件测试和部分真实 API 能力，也对流程模板、内容设置、评估题、评估规则等后台页面进行了较深的视觉还原。

但当前开发投入过多集中在后台配置页面的像素细节、采集缺口和局部交互修复上。部分功能虽然已有大量组件、测试和视觉证据，完整业务主链路仍未形成可持续验收的端到端闭环，开发者容易产生“局部越来越精确、整体业务仍未跑通”的感受。

本决策用于调整后续开发顺序和完成标准：不放弃高质量 UI，也不再把全系统像素级还原作为所有功能的前置条件。

## 2. 现状梳理

### 2.1 已经建立的业务基线

当前基线已经明确：

- 绩效是 HR Portal 内边界独立的模块化业务应用；
- HR Portal 控制应用入口，绩效系统独立控制内部角色、权限和数据范围；
- 绩效流程采用时间节点驱动，节点可并行或重叠开放；
- 周期启动后固化人员、组织关系、流程、等级、权重、处理人和规则快照；
- 工作总结、自评、上级评价、项目评价、校准、发布和申诉分开存储、独立审计；
- 结果链路为评价初算、校准、可选复核、发布和申诉结果覆盖；
- 前端继承 HR Portal 设计系统，不建立第二套基础视觉体系。

权威基线分别见 `overview.md`、`workflow-design.md`、`permission-model.md`、`data-model.md`、`integration.md` 和 `requirements.md`。

### 2.2 已有开发进展

根据当前规格记录：

- PM-001 角色与授权基础任务已完成；
- PM-T002 绩效后台入口、独立设置壳和菜单基础已完成；
- PM-T003 周期创建需求和 UI 蓝图已确认，部分任务已实现，但周期列表、表单、锁定和人员快照等主任务仍未全部完成；
- PM-T004 模板创建已积累大量流程设置、内容设置、执行人规则、组件复用、API 规范化和截图证据，但功能整体仍为 `incomplete`，像素还原仍为 `blocked`；
- PM-T005 评估题规格和部分实现较深入，但完整像素验收仍受采集与 rendered diff 缺口阻塞；
- PM-T006 评估规则的大部分结构、行为和使用状态已实现，完整跨层与像素验收尚未全部结束；
- PM-T007 标签填写题处于开发中，当前仍包含 fixture-only 范围和未冻结的数据/API 契约。

以上状态只代表规格文档记录，不自动等同于当前运行环境、生产环境或全部测试已经通过。任何完成声明仍需按任务重新验证。

### 2.3 当前主要问题

#### 问题一：后台配置页承担了过多像素级工作

模板、评估题和评估规则属于高密度配置页面，天然包含大量字段联动、弹层、拖拽、锁定、权限、校验和异常状态。逐个状态进行像素级采集和验收，成本远高于普通页面。

#### 问题二：视觉精度和业务完成度使用了同一个门槛

采集证据不完整时，像素级验收必须 blocked；但这不应自动阻止不依赖缺失视觉证据的后端契约、业务状态、API 集成和 P0/P1 级 UI 开发。必须区分：

- 业务是否可实现；
- UI 是否可用；
- 结构视觉是否达标；
- 像素级还原是否有完整证据并已验收。

#### 问题三：容易先完成孤立纯 UI，再补业务和 API

复杂业务页面如果先按截图建立孤立 UI，后续接入权限、字段联动、锁定、错误处理和真实 API 时，组件边界和页面结构经常需要返工。

#### 问题四：整体规格已经较完整，但最小业务闭环仍需收敛

当前不缺另一份更大的总体说明，缺的是按纵向业务切片冻结的角色、状态、权限、快照、API、持久化和验收契约。

## 3. 核心决策

### 3.1 业务骨干优先，不以全系统像素级还原作为开发前置

后续优先级调整为：

```text
业务规则与领域边界
-> 后端契约、权限、快照和审计
-> 最小可运行的前后台闭环
-> 关键用户页面高精度还原
-> 低频后台页面像素收口
```

“业务骨干优先”不等于使用粗糙 UI，也不等于先把全部后端开发完再统一开发前端。后续采用纵向切片，每个切片同时包含必要后端、必要后台配置、用户端页面和真实验收。

### 3.2 UI 使用三级完成标准

#### P0：业务可用

必须满足：

- 路由、权限和身份正确；
- 页面可以完成核心操作；
- 字段规则和状态流转正确；
- 数据通过真实 API 保存并可重新打开；
- 加载、空状态、错误、无权限和危险操作有明确反馈；
- 关键行为有自动化测试。

#### P1：结构与设计系统一致

在 P0 基础上满足：

- 页面结构和参考截图的信息层级一致；
- Header、导航、内容区、表单、卡片、表格和弹窗布局合理；
- 使用统一 Token、基础组件、字体、颜色、间距和交互反馈；
- 不出现明显视觉偏差、溢出和不可操作问题；
- 在约定 viewport 下完成运行时人工或截图检查。

#### P2：像素级还原

在 P0/P1 基础上，只有目标状态证据完整时才进入：

- 精确几何、间距、字体、图标、边框、阴影和滚动行为；
- default、hover、focus、active、disabled、expanded、dragging 等适用状态；
- extracted contract 与 rendered contract 比较；
- 目标截图与实现截图 diff；
- 明确报告 passed、blocked 或 not-run。

没有完整证据时不得猜测并宣称 P2 完成，但可以在不影响业务的前提下完成 P0/P1。

### 3.3 不同页面采用不同默认精度

| 页面类型 | 默认目标 | 说明 |
|---|---|---|
| 后端领域、API、迁移、权限 | 业务正确 | 不存在像素目标，优先稳定契约、快照、事务、审计和兼容性 |
| 管理员后台低频配置页 | P0 + P1 | 先做到真实可用、结构一致；P2 延后或仅覆盖关键状态 |
| 管理员高风险操作页 | P0 + P1，关键状态可 P2 | 删除、发布、锁定、校准等必须优先保证防误操作与反馈 |
| 员工填报页 | P0 + P1，核心流程 P2 | 用户覆盖面和使用频率高，优先投入体验与视觉还原 |
| 上级、项目负责人、校准人评价页 | P0 + P1，核心操作 P2 | 重点保证填写效率、上下文清晰和状态反馈 |
| 结果查看与结果沟通页 | P0 + P1，优先 P2 | 是员工对绩效系统的核心感知页面 |
| 公共布局、Token 和共享组件 | 尽早稳定至 P1/P2 | 一次校准后被多页面复用，投入回报高 |

### 3.4 复杂业务页面不先开发孤立纯 UI

管理员配置页默认输入必须同时包含：

1. 参考截图或蓝图；
2. 角色和权限；
3. 字段及联动逻辑；
4. 页面和业务状态；
5. API 请求、响应和错误码；
6. 保存、重开、锁定和审计规则；
7. 本次范围与非范围；
8. 测试和验收标准。

允许先做纯视觉工作的情况仅限：

- 用于确认信息架构和视觉方向的临时蓝图；
- 跨页面复用的基础组件与设计 Token；
- 已明确标记为 fixture/mock 且不被视为功能完成的隔离预览。

fixture 可以用于并行开发，但只有真实 API 保存、读取和重开验证通过后，业务页面才能声明 P0 完成。

## 4. 后续开发建议

### 4.1 先收敛现有后台工作，不继续无边界扩张

对 PM-T004、PM-T005、PM-T006 和 PM-T007：

- 保留已完成的组件化、设计 Token 和高价值视觉成果；
- 优先补齐真实 API、保存、重开、锁定、权限和关键错误状态；
- 未采集且不影响主链路的 hover、resize、次要菜单和低频变体，不再默认阻塞业务主线；
- 任何新增字段、角色、节点类型或运行时规则必须进入独立任务，不继续堆叠到已有 UI 修复子任务；
- 已达到 P0/P1 的后台页面先冻结，P2 缺口进入明确的后续清单。

### 4.2 优先打通第一个端到端业务闭环

建议第一条完整链路为：

```text
管理员创建周期
-> 选择已存在的流程/评价模板
-> 配置参与人员
-> 启动周期
-> 固化周期人员和流程快照
-> 为员工生成工作总结和自评任务
-> 员工提交工作总结
-> 员工提交自评
-> 直属上级提交评价
-> 生成可发布结果
-> 管理员发布
-> 员工查看结果
```

第一条闭环暂不强制包含：

- 多项目复杂权重；
- 多级校准完整能力；
- 强制分布全部算法；
- 多步骤申诉；
- 飞书消息提醒；
- 所有模板和题型变体；
- 全页面像素级还原。

如上述非范围实际成为闭环前置，必须先更新规格说明其必要性，不得在实现过程中静默扩张。

### 4.3 后端优先稳定不可逆和历史敏感能力

在增加页面数量前，优先确认并测试：

- 周期状态及可执行动作；
- 周期启动事务；
- 人员、组织关系、模板、节点和规则快照；
- 节点任务生成和处理人解析；
- 时间窗口、最晚提交和逾期规则；
- 提交幂等性与并发处理；
- 结果计算、校准、发布和申诉覆盖边界；
- 已启动周期不被实时花名册和后续模板修改静默改写；
- 敏感字段可见范围；
- 审计事件及调整前后值。

### 4.4 前端优先投入高频和高感知页面

P2 资源优先投入：

1. 员工工作总结和自评；
2. 上级评价和项目评价；
3. 员工结果查看；
4. 结果沟通、校准和申诉；
5. 高频共享布局和基础组件。

管理员后台继续保证 P0/P1，但除非页面高频、高风险或已经有完整证据，不默认要求所有状态达到 P2。

### 4.5 使用停止规则控制视觉返工

每个 UI 任务开始前必须声明本轮目标为 P0、P1 或 P2。达到声明等级后停止本轮工作，不因临时观察到的非范围像素差异无限新增修复任务。

允许继续修复的条件：

- 阻塞主要操作；
- 破坏权限、安全、持久化或状态正确性；
- 明显破坏统一设计系统；
- 属于本轮已确认的 P2 状态和证据；
- 用户明确提升该页面的精度优先级。

其他视觉差异进入待办，不阻塞当前纵向切片。

## 5. 与 AI 交互的建议

### 5.1 每次只交付一个可验收任务

不要只说“把这个绩效页面做出来”或“像飞书一样”。应提供：

- 当前功能和任务 ID；
- 目标角色和用户场景；
- 必读规格；
- 参考截图对应的状态；
- 本轮 UI 等级；
- 业务规则；
- API 契约；
- 允许和禁止修改的文件；
- 非范围；
- 验收步骤。

### 5.2 推荐的任务输入模板

```text
当前功能/任务：
目标角色与场景：
业务目标：
必读规格：
参考截图/蓝图：
截图对应 viewport、数据和状态：
本轮 UI 目标：P0 / P1 / P2

已确认业务规则：
1.
2.

页面状态：
- loading
- empty
- editable
- saving
- error
- forbidden
- locked（如适用）

API：
- GET：
- POST/PATCH/DELETE：
- 错误码：
- 保存后行为：
- 重开验证：

允许修改：
禁止修改：
明确非范围：

验收：
- 聚焦测试
- 类型检查/构建
- UI -> API -> 数据库/服务 -> GET 重开
- 运行时截图或 rendered contract（仅 P2 强制）
```

### 5.3 AI 开始开发前必须复述边界

AI 在编辑业务代码前必须明确：

- 当前 Spec、功能目录和原子任务；
- 已读取文件；
- 本次修改范围和非范围；
- 是否涉及 UI、数据库迁移、权限、UCP 或外部系统；
- 当前 UI 目标等级；
- 已确认假设和阻塞问题；
- 计划运行的测试和验收。

如果 AI 无法说明这些内容，不应开始跨层修改。

### 5.4 截图只负责视觉，不负责推导业务

不得根据一张截图自行发明：

- 字段及枚举；
- 角色和权限；
- 保存逻辑；
- 状态流转；
- 锁定规则；
- 计算逻辑；
- 错误处理；
- 数据库字段。

截图未覆盖的视觉状态：

- P2 任务中记为 blocked 或 not observed；
- P0/P1 任务中可以按现有设计系统实现合理默认，但必须标明不是像素级结论；
- 不得用近似实现宣称与参考系统一致。

### 5.5 逻辑描述也不能替代视觉证据

业务描述可以决定字段和行为，但不能用于宣称精确的尺寸、颜色、图标、hover 或弹层位置。P2 必须使用真实目标状态及运行时比较。

### 5.6 要求 AI 优先复用，而不是逐页复制

每次开发前先检查：

- 是否已有绩效共享组件；
- 是否已有相同字段和状态机；
- 是否已有相同 API 类型；
- 是否已有统一 Token 和 Element Plus override；
- 是否会产生重复 SVG、重复下拉、重复弹窗或重复预览渲染器。

页面负责组装，业务组件负责领域行为，基础组件负责统一视觉和交互。禁止为了局部像素修复复制一套近似组件。

### 5.7 要求 AI 如实报告验证结果

AI 必须分别报告：

- 已通过；
- 未运行；
- 被阻塞；
- 仅 fixture/mock；
- 仅隔离预览；
- 已连接真实 API；
- 已完成重开验证；
- 已完成运行时视觉验收。

测试、HTTP 200、构建成功、截图存在不能互相替代。

## 6. 分阶段开发路线

### 阶段 0：重新冻结主线与完成等级

目标：阻止后台像素任务继续无边界扩张。

行动：

- 为当前功能标记 P0/P1/P2 目标；
- 盘点 PM-T003 至 PM-T007 的真实完成状态；
- 将“业务阻塞”和“像素阻塞”分开；
- 列出第一条纵向闭环的必要前置；
- 未进入第一闭环的 P2 任务暂缓。

完成标准：有一份按依赖排序的主线任务列表，每项均有明确完成等级、输入输出契约和非范围。

### 阶段 1：周期启动骨架

目标：管理员可以建立和启动一个真实周期。

行动：

- 完成周期列表、新建、编辑和删除；
- 选择模板、等级和参与人员；
- 冻结周期状态机；
- 实现启动事务；
- 生成人员、组织关系和流程节点快照；
- 建立启动前校验、权限和审计。

UI 默认：管理员页面 P0 + P1。

完成标准：周期启动后，修改实时花名册或模板不会改写该周期快照；重新打开数据一致。

### 阶段 2：节点任务与员工填报

目标：周期启动后自动生成员工可操作任务。

行动：

- 生成节点任务和处理人；
- 实现节点开放窗口；
- 实现工作总结和员工自评；
- 分开保存、提交和锁定；
- 建立员工工作台或最小任务入口。

UI 默认：员工核心填报页 P0 + P1，稳定后优先 P2。

完成标准：真实员工身份可打开任务、保存草稿、提交并重新查看；越权和过期操作被拒绝。

### 阶段 3：评价和结果初算

目标：直属上级和必要评价人可以完成评价并生成初步结果。

行动：

- 完成上级评价；
- 接入必要的评估题和评估规则；
- 只启用第一闭环需要的题型和规则；
- 实现分数/等级计算和缺失评价处理；
- 建立评价提交、锁定、审计和可见范围。

UI 默认：评价页 P0 + P1，核心填写状态 P2。

完成标准：从员工提交到上级评价再到初算结果可端到端追踪。

### 阶段 4：发布与员工结果查看

目标：管理员可以发布，员工可以查看稳定结果。

行动：

- 冻结发布前置条件；
- 保存发布快照；
- 实现员工可见字段过滤；
- 实现结果查看和结果沟通；
- 建立发布权限、不可逆确认和审计。

UI 默认：结果查看页优先 P2；管理员发布页 P0 + P1，危险确认状态重点优化。

完成标准：发布后员工只能看到允许公开的信息，内部校准说明和敏感过程不泄露。

### 阶段 5：校准、强制分布、项目评价和申诉

目标：在基础闭环稳定后增加复杂分支。

建议顺序：

1. 部门/组织校准；
2. 公司级校准；
3. 强制分布；
4. 项目评价和多项目权重；
5. 申诉提交与处理；
6. 可选结果修正/复核。

进入每项前先解决 `open-questions.md` 中对应业务决策。未确认算法、可见范围或处理人规则时，不得通过 UI 猜测后端语义。

### 阶段 6：视觉收口与体验统一

目标：在业务和 API 稳定后集中处理高价值视觉差异。

行动：

- 统一共享组件和设计 Token；
- 优先验收员工填报、评价和结果页；
- 再处理管理员高频、高风险页面；
- 对已有完整证据的页面执行 rendered contract 和截图 diff；
- 对无完整证据的页面保持 P1，不虚报 P2；
- 清理重复样式、重复组件和临时 fixture。

完成标准：P2 页面有真实运行时证据；其他页面至少达到 P0/P1，并有明确未完成清单。

### 阶段 7：飞书集成、通知与分析增强

目标：在核心绩效链路稳定后增加外围能力。

包括：

- 飞书 SSO；
- 飞书消息和待办；
- 管理分析报表；
- 更复杂的项目权重；
- 管理员特殊纠错；
- 其他自动化能力。

这些能力不得反向破坏周期历史快照和绩效独立权限边界。

## 7. 全局执行规则

后续 AI 处理任何绩效任务时，默认遵循以下规则：

1. 先读 `START_HERE.md` 和本 ADR，再判断当前任务属于业务、后端、管理后台、员工端还是像素验收。
2. 默认目标不是全系统 P2；任务没有明确声明时，管理员后台按 P0 + P1，员工核心页面按 P0 + P1 并评估是否进入 P2。
3. 不允许用采集缺口阻塞无关后端或业务任务，也不允许绕过采集缺口宣称像素通过。
4. 不单独交付与业务契约脱节的复杂页面纯 UI；蓝图、共享组件和明确 fixture-only 预览除外。
5. 每个纵向切片必须能够从 UI 追踪到真实 API、服务/数据库、读取/重开和权限结果。
6. 周期启动后的人员、组织、流程和规则快照视为历史数据，禁止被实时数据静默改写。
7. 未确认的角色、权限、算法、状态或可见范围先进入 `open-questions.md` 或功能规格，不得由 AI 自行决定。
8. 页面截图不定义业务，业务描述不定义像素；二者分别使用各自真源。
9. 优先复用绩效共享组件和统一设计系统，不为单页近似效果复制组件或建立第二套 Token。
10. 每次只实施已确认的原子任务；达到本轮 P0/P1/P2 目标后停止，不无限扩张。
11. 完成状态必须区分测试通过、构建通过、真实 API 通过、重开通过和运行时视觉通过。
12. 不得因局部像素优化延迟第一条完整业务闭环，除非该差异阻塞主要操作、安全、权限或数据正确性。

## 8. 给 AI 的简版全局指令

用户在新会话中可直接引用本 ADR，或复制以下内容：

```text
本次绩效开发遵循 ADR-002：业务骨干优先、UI 分级还原。

先确认当前原子任务和纵向业务链路，再开发。管理员后台默认做到 P0 业务可用 + P1 结构和设计系统一致，不默认追求全状态像素级；员工填报、评价和结果查看属于高优先级体验页面，业务稳定且证据完整后进入 P2。

复杂业务页面不得只按截图开发孤立纯 UI。开始前必须同时确认角色权限、字段联动、状态、API、保存重开、错误处理、范围和验收。截图只决定视觉，不能推导业务；业务描述不能替代像素证据。

采集证据缺失时，不得猜测并宣称像素通过；但如果缺口与当前业务任务无关，不得阻塞 P0/P1 和后端主线。每个切片都要验证 UI -> 真实 API -> 服务/数据库 -> GET 重开，并保护周期历史快照。

达到本轮声明的 P0/P1/P2 等级后停止，不因非范围像素差异无限扩张任务。如发现未确认的角色、权限、算法、状态、可见范围或共享契约，先报告阻塞，不自行发明。
```

## 9. 候选方案与取舍

### 方案 A：继续全后台像素级优先

优点：后台局部页面可快速接近参考系统。

缺点：采集和验收成本高，业务闭环延迟，API 和状态变更会造成视觉返工。否决。

### 方案 B：先完成全部后端，最后统一开发前端

优点：后端可能较早稳定。

缺点：前端无法及时暴露业务和交互问题，最终集成风险集中。否决。

### 方案 C：纵向业务切片 + 分级 UI 还原

优点：业务、数据和用户体验可以逐步验收；高精度投入集中在高价值页面；保留已有采集和组件成果。

缺点：需要严格声明每项任务的 UI 等级和非范围，并维护业务完成与像素完成两个状态。采用。

## 10. 迁移计划

本决策不要求立即删除或重写已有 UI、规格、采集契约和测试。

迁移方式：

1. 保留已有成果和历史证据；
2. 新任务开始时增加 P0/P1/P2 目标；
3. 盘点未完成任务，将业务阻塞与像素阻塞分开；
4. 将不影响第一闭环的 P2 工作后移；
5. 优先完成 PM-T003 周期与运行时主线所需能力；
6. 逐步把 fixture-only 页面接入真实 API；
7. 业务稳定后再执行高价值页面的 P2 验收。

## 11. 风险与提醒

- 不追求 P2 不等于允许低质量、不可用或不一致的 UI；P0/P1 仍是强制标准。
- 管理员页面虽然低频，但配置错误影响范围大，权限、校验、确认、错误恢复和审计不能降级。
- 第一闭环不得使用临时逻辑绕过快照和权限，否则后续返工成本高于当前收益。
- 不要为了复刻目标系统而复制其不适合本项目的业务限制；视觉参考与业务真源必须分离。
- 任何外部页面采集和资源使用必须保持已授权、安全和合规，不提交凭据、Cookie、Token、未审查生产资源或敏感数据。
- 当前未提交改动较多，后续任务必须保护无关工作树变更，禁止顺手重构或覆盖相邻功能。

## 12. 复查条件

出现以下情况时复查本决策：

- 第一条端到端绩效闭环已经稳定运行；
- 核心员工端页面已经进入集中视觉优化阶段；
- 管理员反馈表明后台视觉差异显著影响配置效率；
- 已建立低成本、稳定的自动截图 diff 流水线；
- 参考系统或本项目设计系统发生重大变化；
- 业务团队明确要求某一后台页面成为高频或对外展示页面。

复查时可以提高或降低具体页面的 UI 等级，但不得取消业务正确、真实持久化、权限、历史快照和 UI 验收这些底线。
