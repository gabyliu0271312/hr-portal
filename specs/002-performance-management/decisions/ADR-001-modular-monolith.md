# ADR-001：绩效采用模块化单体建设

- 状态：已确认
- 日期：2026-08-03
- 范围：绩效管理第一期及后续可拆分准备

## 背景

绩效管理是长期建设的大型业务应用，但第一期需要复用 HR Portal 的登录态、应用入口、员工实时花名册来源、数据库基础设施和统一发布链路。

## 决策

绩效暂时建设在现有 HR Portal 仓库和 Compose 运行环境内，采用模块化单体：

- 后端使用独立的 `backend/app/performance/` 模块和 `/api/v1/performance/*` API 前缀。
- 前端使用独立的 `PerformanceLayout`、绩效路由和 `views/performance/` 页面目录。
- 数据使用绩效领域表命名和独立迁移，周期启动后保存人员与组织关系快照。
- 绩效内部角色、权限、流程、结果、申诉和审计逻辑不散落到 Portal 通用模块。
- 第一阶段不建立独立 Git 仓库、独立后端容器、独立前端容器或独立数据库实例。

## 取舍

优点：减少 SSO、跨服务 API、CORS、数据同步、版本协调和部署联调成本；可以保持一次提交内的前后端、权限和迁移一致性。

代价：初期发布和扩容边界与 HR Portal 共享，需要严格遵守模块边界和领域命名，避免形成不可拆分的耦合单体。

## 后续拆分条件

只有当绩效拥有稳定的独立 API 契约、独立团队与发布节奏、独立扩容/SLA 需求、独立身份和人员同步方案，并能承担跨服务一致性成本时，才重新评估拆分仓库、容器和数据库。

## 影响

后续所有绩效需求应优先更新 `specs/002-performance-management/` 下的功能规格、ADR、UI 蓝图和原子任务，不得因为“系统很大”而直接复制一套 Portal 基础设施。
