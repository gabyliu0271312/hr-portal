## 1. 需求说明

### 1.1 业务背景

现有数据对比 Skill 支持对两张表在一个固定月份内执行名单、字段或金额对比。例如：

> 对比 2026 年 6 月月度花名册与月度工资表的员工名单。

业务需要一次覆盖连续多个月份，并将结束月份设置为动态值。例如：

> 对比 2026 年 1 月至今，月度花名册与月度工资表的员工名单。

该配置保存后，每次手动或定时运行时，系统都应按**自然月当前月**重新确定结束月份，而不是固定在首次保存当月。

### 1.2 核心需求

1. 支持一次配置并执行连续多个月份的双源数据对比。
2. 支持固定结束月，例如“2026.01 至 2026.06”。
3. 支持动态结束月 `current_month`，例如“2026.01 至今”。
4. `current_month` 固定表示服务端业务时区下的**自然月当前月**。
5. 每次运行均重新解析动态结束月；保存的配置保留逻辑表达式，不把“至今”固化成首次运行月份。
6. 多月对比采用**逐月独立执行、按月汇总展示**的方式：A 表 `202601` 对 B 表 `202601`，依次类推。
7. 若任一参与对比的月度表在某一月份**完全没有数据**，该月份必须预警为“数据未完成”，不得当作“无差异”或“对比通过”。
8. 执行结果必须保存本次请求范围、解析时刻、实际月份列表、每月状态及汇总结果，便于审计和复现。
9. 既有单月配置、三类对比模板、安全白名单、行级权限、脱敏与自动化能力必须保持兼容。

### 1.3 用户故事

| 编号 | 用户故事 | 验收价值 |
|---|---|---|
| MP-US-01 | 作为 HR 管理员，我希望输入“对比 2026 年 1 月至今的月度花名册和工资表名单”，以便每次执行都覆盖当前自然月。 | 不必每月手工修改配置。 |
| MP-US-02 | 作为任务维护者，我希望保存“2026.01 至今”后，在 8 月与 9 月执行时分别比较至 202608 与 202609。 | 动态期间配置可复用。 |
| MP-US-03 | 作为数据核验人员，我希望按月查看对比结论和差异明细，以便准确定位发生问题的月份。 | 避免跨月结果混淆。 |
| MP-US-04 | 作为自动化任务接收人，我希望当任一来源表当月完全无数据时收到“数据未完成”预警，而不是收到一致结论。 | 避免把未同步误判为对账异常或成功。 |
| MP-US-05 | 作为审计人员，我希望知道某次“至今”任务实际比较了哪些月份。 | 可回查、可解释。 |

### 1.4 非目标

本次扩展不包含以下能力：

- 多月趋势、环比、同比、累计趋势图或跨月变化分析。
- 将多个期间合并为一条跨月大 SQL 后进行总体名单、字段或金额对比。
- A/B 不同月份映射，例如“工资 202606 对分摊 202607”。
- 离散月份列表、最近 N 月、财年、滚动窗口等复杂时间 DSL。
- 三张及以上表联查。
- 修改数据、补数、自动触发上游同步。
- 对非月度实时表补建历史快照。

这些能力若后续需要，应另行立项，不应通过放宽本需求的 CompareSpec 或固定 SQL 模板实现。

## 2. 现状分析

### 2.1 既有能力

基础规格中的 `CompareSpec` 已覆盖：

- 两个数据源 `source_a` 与 `source_b`。
- 三类固定对比引擎：`roster`、`field`、`amount`。
- 单一 `period` 参数：月度表必须指定 `YYYYMM`，非月度表可为 `null`。
- 表和字段元数据白名单、封闭的 `prefilter.op`、参数化 SQL 模板。
- `scope_strategy` 行级权限过滤、敏感字段脱敏、30 秒查询超时和结果行数限制。
- 已保存 Skill、执行记录、定时调度和飞书摘要通知的设计。

### 2.2 现状限制

| 现状 | 限制 | 对本需求的影响 |
|---|---|---|
| `DataSource.period` 为单个字符串 | 只能表达一个固定 `YYYYMM` | 无法表达“202601 至今”。 |
| 三类模板一次仅接收一组 A/B 月份参数 | 假设一次调用只进行单月比较 | 不可直接承载逐月执行与结果聚合。 |
| 结果格式只有单次对比摘要与明细 | 没有月份维度 | 多个月明细会混淆。 |
| 执行记录未要求保存逻辑范围与实际解析范围 | 无法解释动态范围运行差异 | 不满足审计与复现。 |
| 自动化状态只有成功、差异、失败语义 | 未定义“部分月份数据未完成” | 可能将未同步数据错误归类。 |

### 2.3 设计结论

本需求是既有双源对比能力上的**时间编排层扩展**，不是新建趋势引擎，也不是修改三套对比 SQL 为跨月聚合 SQL。

推荐执行模式为：

```text
逻辑 CompareSpec（期间范围）
  → 期间解析器（运行时解析 current_month）
  → 逐月执行计划
  → 对每个月生成内部单月 CompareSpec
  → 复用既有 SchemaValidator / CompareTemplateEngine / QueryExecutor / ResultFormatter
  → 按月结果聚合与展示
```

该方案保留既有安全路径，并可识别单月数据缺失、超时或权限异常。

## 3. 功能范围与业务规则

### 3.1 期间语义

#### 3.1.1 支持的期间表达式

首期仅支持以下三种表达：

| 类型 | 配置示例 | 自然语言示例 | 说明 |
|---|---|---|---|
| 单月 | `202606` | “2026 年 6 月” | 与既有能力完全兼容。 |
| 固定连续区间 | `202601` 至 `202606` | “2026 年 1 月至 6 月” | 含起止月的闭区间。 |
| 动态连续区间 | `202601` 至 `current_month` | “2026 年 1 月至今” | 每次运行动态解析截止月。 |

LLM 可以理解“2026.01”“2026 年 1 月”和“202601”，但写入配置前必须统一规范为 `YYYYMM`。

#### 3.1.2 `current_month` 定义

- `current_month` = 服务端统一业务时区下的自然月当前月。
- 业务时区固定为 `Asia/Shanghai`，不得依赖浏览器时区、用户本地时区或数据库服务器默认时区。
- 例如在 `2026-08-04 09:00:00+08:00` 运行，“2026.01 至今”解析为 `202601` 至 `202608`。
- 本需求不根据“双方最新共同有数据的月份”自动截断范围。

#### 3.1.3 期间对齐

首期固定为 `same_period`：

```text
A(202601) ↔ B(202601)
A(202602) ↔ B(202602)
...
```

不支持期间偏移、跨月映射或自动推断月份对应关系。

### 3.2 数据未完成判定

#### 3.2.1 判定规则

对于某个实际执行月份：

- 若 A、B 均为月度表，且 A 或 B 中任一表在该月份按既有权限与前置过滤条件查询后**完全没有数据**，该月份状态为 `data_incomplete`。
- `data_incomplete` 是数据就绪预警，不是“名单/字段/金额差异”。
- 系统必须在该月结果中标明缺少数据的来源：`source_a`、`source_b` 或 `both`。
- 该月份不进入三类差异模板的正常一致性结论计算。
- 其他已就绪月份继续执行；单月数据未完成不能导致整个多月任务丢失已完成月份结果。

#### 3.2.2 与“无数据”“无权限”“执行失败”的区分

| 状态 | 判定 | 用户可见含义 |
|---|---|---|
| `success` | 两侧数据就绪，且无差异 | 对比完成，无差异。 |
| `partial_diff` | 两侧数据就绪，且存在差异 | 对比完成，存在差异。 |
| `data_incomplete` | 至少一张月度表该月完全无数据 | 数据未完成，不能下对账结论。 |
| `no_data` | 非月度/特殊配置下查询范围无数据，或经后续规则明确判定 | 无可比较数据；不得等价为一致。 |
| `failed` | 校验、权限、查询、超时或系统异常导致不能执行 | 对比未完成，需查看错误。 |

> 注：是否以“应用了 `prefilter` 后无数据”判为 `data_incomplete`，首期按“实际参与对比的数据范围”判定，即应用既有权限和 `prefilter` 后的结果为准。前端需展示已应用过滤条件，避免误解为源表整体未同步。

### 3.3 多月执行与总体状态

1. 多月任务按月份独立执行，默认顺序执行或使用受控并发；不得无限并发占用数据库连接。
2. 每个子执行都必须复用既有的表/字段白名单、期间过滤、`scope_strategy`、敏感字段脱敏、查询超时及行数限制。
3. 总体状态规则：

| 总体状态 | 条件 |
|---|---|
| `success` | 所有月份均执行完成且均无差异。 |
| `partial_diff` | 至少一个已完成月份有差异，且不存在失败或数据未完成月份。 |
| `partial_success` | 至少一个月份成功或发现差异，但同时存在 `data_incomplete` 或 `failed` 月份。 |
| `failed` | 范围解析、配置校验失败，或没有任何月份产生可用结果。 |

4. 总 `diff_count` 只统计状态为 `partial_diff` 的月份中产生的实际差异记录，不将 `data_incomplete` 计入差异数。
5. 月份数量超过系统限制时，系统拒绝执行并提示缩小范围；首期建议交互执行上限为 12 个月、自动化任务上限为 24 个月，具体阈值须在开发前冻结。

### 3.4 非月度表边界

- 本需求的完整“按月双源对账”仅适用于 A/B 都是月度表的场景。
- 月度表对实时非月度表的既有单月字段比对保持可用，但不应被宣传为历史逐月对账：实时表始终读取运行时快照。
- 首期多月范围如包含非月度表，应在创建/保存前明确提示“非月度来源为当前快照，无法代表各月历史数据”；是否允许执行须由产品与业务在开发前确认。
- 默认建议首期仅允许两个来源均为月度表时使用多月范围，避免产生历史含义误导。

## 4. CompareSpec 扩展设计

### 4.1 兼容原则

- 保留既有 `source_a.period` / `source_b.period`，用于历史单月配置和运行时展开后的内部子任务。
- 新增 `period_range` 表达逻辑范围；`period` 与 `period_range` 互斥。
- 已保存的单月 Skill 不迁移、不改变原有执行结果。
- 新增配置仅在两个来源均为月度表时允许使用 `period_range`。

### 4.2 建议数据结构

```json
{
  "compare_type": "roster",
  "source_a": {
    "table": "emp_monthly_roster",
    "period": null,
    "period_range": {
      "type": "range",
      "start": "202601",
      "end": "current_month"
    },
    "prefilter": []
  },
  "source_b": {
    "table": "emp_monthly_salary",
    "period": null,
    "period_range": {
      "type": "range",
      "start": "202601",
      "end": "current_month"
    },
    "prefilter": []
  },
  "period_execution": {
    "mode": "per_period",
    "alignment": "same_period"
  },
  "join_keys": ["employee_no"],
  "output": {
    "only_diff": true,
    "max_detail": 200
  },
  "roster": {
    "direction": "both",
    "display_fields": ["employee_no", "employee_name", "department"]
  }
}
```

### 4.3 字段约束

| 字段 | 规则 |
|---|---|
| `period_range.type` | 首期固定 `range`。单月继续使用既有 `period`。 |
| `period_range.start` | 必填，格式 `YYYYMM`。 |
| `period_range.end` | 必填，格式 `YYYYMM` 或字面量 `current_month`。 |
| `period` 与 `period_range` | 二选一；不得同时存在。 |
| `period_execution.mode` | 首期固定 `per_period`。 |
| `period_execution.alignment` | 首期固定 `same_period`。 |
| 起止顺序 | 解析后 `start` 不得晚于 `end`。 |
| 未来固定结束月 | 默认拒绝；不得静默截断。 |
| 月度表 | 必须具备 `period` 或 `period_range`。 |
| 非月度表 | 不得使用 `period_range`。 |

### 4.4 运行时展开

保存配置：

```json
{"start": "202601", "end": "current_month"}
```

在 `2026-08-04` 执行时，内部展开为：

```text
202601, 202602, 202603, 202604, 202605, 202606, 202607, 202608
```

每一个月份生成一个仅供内部执行的单月 CompareSpec，例如：

```json
{
  "source_a": {"table": "emp_monthly_roster", "period": "202608", "prefilter": []},
  "source_b": {"table": "emp_monthly_salary", "period": "202608", "prefilter": []}
}
```

内部子 Spec 不作为用户配置覆盖写回 `ai_skills.params`。

## 5. 执行、结果与审计需求

### 5.1 执行链路

```text
读取 Skill.params
  → SchemaValidator 校验逻辑 CompareSpec
  → PeriodResolver 以 Asia/Shanghai 解析动态结束月
  → PeriodExecutionPlanner 展开实际月份
  → 对每个月进行数据就绪检查
      → 任一来源无数据：生成 data_incomplete 子结果
      → 两侧就绪：调用既有单月对比执行链路
  → PeriodResultAggregator 汇总子结果
  → ResultFormatter 输出多月结果
  → 保存运行记录、更新最近执行摘要
```

### 5.2 返回结果结构

多月结果必须包含以下信息：

```json
{
  "period_resolution": {
    "requested": {
      "type": "range",
      "start": "202601",
      "end": "current_month"
    },
    "resolved_at": "2026-08-04T09:00:00+08:00",
    "timezone": "Asia/Shanghai",
    "resolved_periods": ["202601", "202602", "202603", "202604", "202605", "202606", "202607", "202608"]
  },
  "status": "partial_success",
  "diff_count": 5,
  "period_results": [
    {
      "period": "202601",
      "status": "success",
      "diff_count": 0,
      "duration_ms": 320
    },
    {
      "period": "202602",
      "status": "partial_diff",
      "diff_count": 5,
      "duration_ms": 380
    },
    {
      "period": "202608",
      "status": "data_incomplete",
      "missing_sources": ["source_b"],
      "diff_count": 0,
      "duration_ms": 90
    }
  ],
  "summary": {
    "success_period_count": 1,
    "diff_period_count": 1,
    "data_incomplete_period_count": 1,
    "failed_period_count": 0
  }
}
```

### 5.3 展示要求

结果卡片与详情页应按以下层次展示：

1. **范围摘要**：用户请求范围、本次实际范围、解析时间与业务时区。
2. **月度汇总表**：月份、状态、差异数量、数据未完成来源、耗时。
3. **差异明细**：按月份折叠；每条差异记录必须携带 `period`。
4. **总体结论**：明确区分“已完成无差异”“存在差异”“数据未完成”“执行失败”。

金额汇总中的跨月差额可以展示为“各月差额累计”，但不得以此替代逐月结论，也不得将其标为单一“整体对账通过/失败”。

### 5.4 明细限制

既有 `output.max_detail` 必须在多月结果中明确解释。首期建议采用：

- `max_detail`：整个任务返回给前端的差异明细总上限。
- 每月仍保存实际差异计数，即使明细已截断。
- 结果中返回 `detail_truncated`、`returned_detail_count` 与按月截断摘要。

### 5.5 持久化与审计

`ai_skills.params`：保存逻辑范围表达式，例如 `end: "current_month"`。

`data_compare_runs.summary`：必须保存：

- 原始 `period_range` 请求；
- `resolved_at`；
- `timezone`；
- `resolved_periods`；
- 每月状态、差异数、缺失来源、耗时；
- 总体状态与各状态月份计数；
- 明细是否截断。

审计日志不得保存未脱敏员工明细、金额明细、SQL 或完整权限范围。

### 5.6 自动化与飞书通知

定时任务运行时同样按运行当时的 `current_month` 解析，不能复用上一次的解析结果。

飞书只推送汇总信息，例如：

```markdown
📊 数据对比完成：2026.01 至今
本次实际范围：202601–202608

- 无差异月份：5
- 存在差异月份：2
- 数据未完成月份：1（202608：月度工资表无数据）
- 执行失败月份：0

👉 查看详情：[Portal 对比详情]
```

飞书不得推送员工姓名、员工编号、部门明细或金额明细。

## 6. 安全与性能要求

### 6.1 安全继承要求

多月编排不得绕开基础规格定义的安全边界：

- LLM 仍仅输出 CompareSpec JSON，不生成 SQL。
- 表、字段、关联键、分组维度和过滤字段仍必须通过 `registered_tables`、`table_columns` 白名单验证。
- 每个期间子任务必须注入相同的 `scope_strategy` 行级过滤。
- 每个期间子任务必须执行敏感字段脱敏、语句超时与行数上限。
- 不支持用户输入 SQL、表名拼接、动态 Join 或动态期间映射表达式。

### 6.2 性能保护

- 每个子任务沿用既有 `statement_timeout = 30s` 与 `max_rows = 10000`。
- 多月任务增加总期间上限、总任务时间预算和受控并发限制。
- 执行不得把所有月份的明细一次性全量读取至应用内存后再比较。
- 数据就绪检查必须使用轻量受控查询，例如受当前 scope 和 prefilter 约束的存在性检查或计数检查。
- 任何一个月超时或失败，应记录该月状态并遵循总体状态规则，不得吞掉错误后伪装为无数据或一致。

## 7. 功能拆解与验收标准

> 以下为开发任务拆分，不代表本次需求文档已开始开发。

### MP-01：CompareSpec 期间范围 Schema

**目标**：让配置可表达固定连续区间与“至今”。

**范围**：

- 新增 `period_range` 与 `period_execution` Schema。
- 保持既有单月 `period` 配置兼容。
- 实现 `period` 与 `period_range` 互斥、月份格式、月度表要求、非月度表限制等校验。
- 更新 AI Prompt / 结构化输出契约，使自然语言“2026.01 至今”输出合法结构。

**验收标准**：

- [ ] `2026.01 至 2026.06` 被规范化为 `start=202601, end=202606`。
- [ ] `2026.01 至今` 被规范化为 `start=202601, end=current_month`。
- [ ] 单月历史配置可继续校验、保存和执行。
- [ ] `period` 与 `period_range` 同时传入时明确拒绝。
- [ ] 非法月份、起止倒置、未来固定结束月、非月度表使用 `period_range` 均明确拒绝。

### MP-02：动态期间解析与执行计划

**目标**：在每次执行时解析实际月份，并拆分为受控单月子任务。

**范围**：

- 新增 `PeriodResolver`，按 `Asia/Shanghai` 解析 `current_month`。
- 新增 `PeriodExecutionPlanner`，生成连续月份的内部单月 CompareSpec。
- 支持跨年展开、最大月份数限制与执行预算。
- 首期只支持 `per_period + same_period`。

**验收标准**：

- [ ] 在 2026-08-04 运行“2026.01 至今”生成 202601 至 202608。
- [ ] 在 2026-09-01 运行同一配置生成 202601 至 202609。
- [ ] 跨年区间可正确展开，例如 202511 至 202602。
- [ ] 每个内部子任务只持有一个固定月份。
- [ ] 超出期间上限时明确拒绝，不静默截断。

### MP-03：月度数据就绪检查

**目标**：识别任一参与来源在某月完全无数据的情况。

**范围**：

- 在进入既有对比模板前执行按月数据存在性检查。
- 在应用当前用户权限和配置 prefilter 后判断每个来源是否存在数据。
- 生成 `data_incomplete` 及 `missing_sources`。
- 保持其他月份继续执行。

**验收标准**：

- [ ] A 表有数据、B 表无数据时，结果为 `data_incomplete` 且标记 `source_b`。
- [ ] A、B 均无数据时，结果为 `data_incomplete` 且标记双方。
- [ ] 数据未完成月份不计入差异数，也不显示为无差异。
- [ ] 已就绪月份继续按既有三类模板执行。
- [ ] 无权限、超时和系统错误不被错误归为 `data_incomplete`。

### MP-04：多月结果聚合与执行记录

**目标**：将按月子结果形成可理解、可审计的总结果。

**范围**：

- 新增按月结果与总体摘要数据结构。
- 支持 `success`、`partial_diff`、`data_incomplete`、`failed` 子状态及 `partial_success` 总体状态。
- 扩展 `data_compare_runs.summary/detail` 的期间解析与按月结果字段。
- 定义全任务明细截断规则。

**验收标准**：

- [ ] 每月结果都带 `period`、状态、差异数、耗时和必要原因。
- [ ] 动态运行记录保存逻辑范围、实际范围、解析时间与时区。
- [ ] 总体状态符合第 3.3 节规则。
- [ ] 差异明细均带 `period`，前端可按月定位。
- [ ] 历史运行可解释同一“至今”配置在不同日期覆盖不同月份。

### MP-05：前端结果展示与任务配置

**目标**：让用户理解多月范围、数据未完成预警与逐月结论。

**范围**：

- 结果卡片增加范围摘要和月度汇总表。
- 明细按月折叠展示。
- 已保存配置展示“固定区间”或“至今”逻辑范围。
- 数据未完成使用独立视觉状态与说明，不混同差异或失败。

**验收标准**：

- [ ] 用户可看到请求范围、实际解析范围和运行时区。
- [ ] 月度汇总展示无差异、差异、数据未完成和失败的不同状态。
- [ ] “数据未完成”可看到缺失来源，但不展示敏感数据。
- [ ] 金额场景跨月累计仅标为累计信息，不替代月度结论。
- [ ] 窄屏下月度表和明细可正常阅读。

### MP-06：自动化、飞书与回归测试

**目标**：确保定时任务动态解析月份，并维持既有能力安全和兼容。

**范围**：

- Scheduler 每次触发时重新解析 `current_month`。
- 飞书通知补充实际范围、差异月份数、数据未完成月份数和失败月份数。
- 覆盖单月配置、三类对比、权限过滤、脱敏、超时和明细截断的回归测试。

**验收标准**：

- [ ] 同一自动化任务跨月执行时实际范围自动向后推进。
- [ ] 飞书通知不包含员工或金额明细。
- [ ] 数据未完成月份在飞书摘要中明确标识。
- [ ] 单月 Skill 的结果、保存和运行记录无回归。
- [ ] 每个按月子任务都应用既有权限、超时、行数限制和脱敏。

## 9. 风险与决策

| 风险 | 影响 | 本需求的控制措施 |
|---|---|---|
| 将“至今”按最新有数月份截断 | 与业务已确认的自然月口径不一致 | 固定使用 `current_month`；无数据时明确 `data_incomplete`。 |
| 把多月数据合并后比较 | 重复计数、金额抵消、差异不可定位 | 固定采用逐月执行、按月聚合。 |
| 将“无数据”显示为“一致” | 掩盖上游同步未完成 | 设置独立 `data_incomplete` 状态。 |
| 多个月份导致查询压力骤增 | 数据库超时或连接池耗尽 | 期间上限、总预算、受控并发、继承单月超时。 |
| 多月明细混合展示 | 用户无法定位差异发生月份 | 每条明细强制带 `period`，前端按月折叠。 |
| 动态任务不可复现 | 审计无法解释历史结果 | 保存逻辑范围与本次实际解析范围。 |
| 非月度实时表被误解为历史快照 | 业务结论不可靠 | 首期建议限制多月范围为两个来源均月度表；其他情况显式提示并待评审。 |

## 10. 待确认事项

1. **多月范围是否第一期仅允许两个来源均为月度表？** 本文建议“是”，以避免实时表被误解为历史快照。
2. **期间上限是否采用交互 12 个月、自动化 24 个月？** 如需更大范围，需确认数据库容量、总时长预算和并发策略。
3. **数据就绪检查是否以应用 `prefilter` 后的数据范围为准？** 本文按“是”设计；若业务需要识别源表整体同步状态，应另建同步状态元数据，不应由对比结果反推。
4. **`data_incomplete` 是否需要触发比普通差异更高优先级的飞书提醒？** 本文仅规定摘要必须展示，通知频率和升级规则待业务确认。
5. **现有 `data_compare_runs.status` 若为数据库枚举，是否允许新增 `partial_success`？** 需在开发前确认迁移兼容策略。

## 11. 完成定义

本需求的开发完成需同时满足：

- 支持固定连续区间和“至今”的动态连续区间配置；
- 每次运行按 `Asia/Shanghai` 自然月重新解析 `current_month`；
- 多月按同月对齐、逐月独立执行；
- 任一来源某月完全无数据时准确标记 `data_incomplete`；
- 结果、执行记录、前端与飞书摘要均清楚呈现逻辑范围、实际范围和逐月结论；
- 单月配置与三类既有对比引擎完全兼容；
- 每个按月子任务仍满足白名单、行级权限、脱敏、超时和行数限制；
- 第 7 节所有任务及第 8 节测试场景完成验收。
