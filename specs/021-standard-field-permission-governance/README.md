## 最新补充：期间记录与树能力复用（2026-10-26，接手先读）

本节统一记录本轮讨论结论；若下文或其他021文档的实现表述不一致，以本节澄清为准，不要求为此重排全部任务，本轮不开发或操作生产。

- **字段定义与业务记录粒度分离。**标准字段只定义一次；月度工资不是每月新增工资字段，而是同一结果结构按期间保存多条记录，例如同一Employment的202601/202602工资各一条。“期间性”由业务对象的期间字段、关系和事实粒度表达，不把每个字段改成按月JSON存值。工号属于雇佣属性，工资记录关联批准的雇佣身份；必要的当期工号/组织快照按原口径保留，不能用当前属性覆盖历史含义。
- **B前期先划清职责，不扩重字段目录。**字段层维护编码/名称/类型/业务含义及必要金额、比例、币种和敏感语义；实体/业务对象层明确字段归属、关系、期间字段及记录约束；薪酬/分摊服务阶段再核准真实粒度、来源、批次、修正版本与发布规则。不能假定员工+月份必唯一，不提前建设完整薪酬模型、历史版本引擎或内部核算；已有期间配置/元数据优先核查复用。
- **通用树不是另建一套。**现有组织树、成本中心树、树组装、HierarchyTreePicker、健康检查、层级投影及后代展开是复用主干；B20等“建设通用树”的措辞应理解为提炼共同逻辑、优化组件并补实体/字段可配置接入，而不是重做树模型、服务和页面。仅提炼前端组件不足以支持新树，须核对后端固定组织/中心模型与接口的必要扩展，但只补当前实例缺口。
- **树配置不等于授权策略。**新实体可按编码/名称/父节点/状态配置树；组织是首实例，再用一个非组织实例验收复用。新树不自动授予人员/中心范围权，不能为每种树复制CRUD，也不能随组织实例整合自动切换现网成本树；职级顺序未必是父子层级，不强制成树。

- **现有按月同步继续复用，不重建同步平台。**当前工资/分摊以普通表落库、按月同步；B接入路径为“原同步成功落库→HR对应结果/事实服务按期间接收、校验、发布→只读数据产品供原报表消费”。现有表可保留来源追溯，业务入口/身份/权限由HR服务承担；实际存储复用或迁移先核查，不强制一开始复制全部表或重新获取全部历史数据。
- **按期间处理，覆盖与增量分开。**一次同步202601只作用于该期间，其他期间不受影响；先核对当前同步模式与真实业务记录键，不能统一假定员工+月份唯一。整月覆盖须确认该月来源完整、身份/字段/记录全部校验成功后才替换该月已发布结果；失败不公开部分结果，保留仍安全的旧发布版本。增量只更新明确收到的记录，未返回记录不当删除；同一同步重试不能生成重复业务事实。若沿用物理表，发布结果必须与未成功的来源写入隔离，不能只在界面提示失败而消费者已读到半批数据。
- **同步批次、存量接管与更正可追溯。**来源无批次号时优先复用现有同步运行ID记录接收证据，按需管理业务结果版本，不要求外部先改接口，也不预设来源已有版本字段。先接管一个已有月份，对照身份、行数、金额及原报表口径通过后再逐月扩大；重同步已发布月份形成可追溯更正/发布记录，不无痕覆盖。源表过去已覆盖且无留存的历史修订不得补造；这一结果追溯不扩为通用SCD/历史平台。
- **未来核算切换不改变消费合同。**当前外部已计算结果只读接收，未来内部核算也提交到同一HR结果接收/发布边界，复用标准字段身份、类型/单位/币种与权限；按相同雇佣关系、期间及真实事实粒度并行对账、经批准切换并可安全回退，不让两个生产者相互覆盖。当前不开发内部核算、不自动改绑生产报表或共享出口；本补充细化B后续结果服务，不改变A当前小MVP顺序。

### 1.1 后续AI必须使用的读写顺序

1. 先读本文全部内容，确认生产部署边界和当前唯一下一步。
2. 读spec的范围、用户场景、编号需求/AC、关键规则和本轮待冻结项；只实现已确认需求，不把任务名/测试夹具当成新业务授权。
3. 读mvp-tasks的交付合同、选中卡、§4追踪/状态及§9证据账，核对依赖和对应FR/AC；只选一张卡或一个模板实例，不自行执行整张路线图。
4. 检查git status、当前代码/调用和可访问环境，再复述本轮六项：目标卡/FR/AC、角色与原入口、已核实复用点、不做事项、成功/拒绝验收、实际影响面/停止方式。纯文档任务明确“不开发”；用户未要求开发不自动开工。
5. 开发结束更新该卡及FR/AC证据，分别写代码、SQL/API、PC、部署和生产验收；不能凭“已有实现”标已完成，也不重复开发已满足的能力。

### 1.2 文档权威与变更规则

- 项目安全/执行规则继续适用；业务要求按用户最新明确决定→spec→MVP卡。README只登记事实/启动停点，不另定义业务需求，Git历史/旧快照仅作证据，不能覆盖现行规格。
- 需求与任务冲突时先澄清/修正文档；只要涉及授权范围、计算口径、A/B范围变化，须得到用户确认，不能由AI为让测试通过而改需求。代码/数据库是现状依据，不自动证明已满足规格。
- 一项需求只在spec定义一次；需求编号稳定，任务实例引用FR和AC。当前状态在README/任务账维护，验收记录不另造“新交接文档”或重复规划文件。
- 这些是人工/AI工作协议，不是已实现的自动化拦截；后续接手仍须执行代码/环境核对。项目规则入口见 [仓库CLAUDE.md](../../CLAUDE.md) 与 [HR Portal规则](../../hr-portal/CLAUDE.md)。

## 2. 已确认方向

- 原报表业务逻辑满足需求：保留多表JOIN、公式、逐行系数拆分、透视/转置、维度归并、聚合、尾差、分页、CSV/XLSX及既有字段/列实例语义。

- **整合不是做兼容层。最终一套报表功能、一条正式计算链，不保留长期legacy/authorized双引擎分流。**生产部署分步、记录版本留痕，不代表最终保留双架构。
- **第一批优先收口标准字段目录、模型准入、执行授权**：目录以新建/维护字段定义为主，精简越界/重复操作并逐项删除无引用实现；模型校验整合发布，执行器切换授权退役。保留必要字段/权限/治理证据，不全量舍弃增强。
- **实体定义、实体清单和字段归属放在B第一阶段B00/B01.a**：A当前不加实体下拉、占位对象或默认归属；B新建标准字段时选择同一实体定义的稳定ID，存量逐个确认，不能按名称自动归Person/Employment。
- 冗余代码先查消费者，再迁移必要能力，最后逐模块删除。不得以新切片的“两事实/一关系/不支持派生”限制削减原功能。
- **B不是只建立空实体**：员工/组织等现有表后续要从普通仓库表接入HR业务服务；B前段先建设通用树能力并用组织树作为第一个实例，B后续接入月度工资结果服务和员工分摊事实服务。外部已算工资先只读接收，未来内部核算复用同一结果合同；分摊保留事实粒度/批次/版本并复用A报表权限，不自动放开跨事实计算。

## 6. 开发、生产与安全退役

1. 先检查分支与工作区，避开其他绩效改动；代码审查先行，只为本轮风险补最小测试和必要真实SQL。UI改动必须用PC浏览器走查，手机验收不适用。
2. 开发环境可用合成数据复刻真实六表结构；生产没有开发副本不阻塞代码审查，但合成结果不能冒充生产验收。
3. 先核查全部非legacy消费者与准入/UI调用，不只看报表3/18/20。依赖迁移、权限和原业务口径验证后，才删除对应新执行器/重复入口/废弃测试限制。
4. 采用开发端前向修复提交，经授权推送、由用户部署生产；每个安全独立MVP可单独发布。不整包revert、不强退main、不批量改回legacy、不在生产现场补代码。
5. 保留审批、转换运行、审计与绑定证据；不关闭append-only保护、不降级数据库、不为凑准入改主键/关联、不重建共享DWD。数据库冗余清理另作影响分析、批准和正式迁移。
6. 公共代码修复影响实际推送/定时/API/快照/实时出口时，必须先验证该影响面；无法证明安全则不发布或经批准暂停具体消费，绝不恢复旧越权路径。
7. 开发完成、PG/API通过、PC通过、已部署、生产对象验收分别记录。B在A独立验收后启动；A/B完成均不代表全渠道/历史/HR流程完成。
