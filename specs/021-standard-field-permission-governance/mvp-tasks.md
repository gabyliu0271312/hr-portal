# 021 小MVP任务清单

更新：2026-10-28。需求以 [spec.md](spec.md) 为准；本阶段闭环合同见[B基础前置专项规格](b-foundation-first-spec.md)，环境与下一步见 [README.md](README.md)。这是唯一开发队列及状态/证据账；专项不另建状态表，旧42个父任务仅作范围追踪。

## 1. 每轮交付合同

- **一次一张卡、一个对象、一种主要操作。**同轮完成必要实现、权限负例、最小真实验证和现有入口验收，不拆成多轮“先建表/再接口/以后才UI”。没有UI的盘点/纯清理说明不适用，不强建页面。
- 先复用、后补缺口。已实现且符合本轮要求的能力只复核证据；有价值增强整合原功能，不做兼容壳、不扩建平行引擎；只在无引用且安全承接后删除冗余。
- 只依赖本轮必要具名子项，不等整个父任务或阶段全勾完。生产等待不阻塞独立本地修复，但公共代码发布必须覆盖全部实际影响渠道。
- 每卡至少有：正常操作可用、权限拒绝不泄漏、原业务口径保持、失败/停止明确。先代码审查，只为不能静态证明的风险补最小真库/API；UI必须PC浏览器验证，手机不适用。
- 复用scope_filter/masker、Report/DataSet ACL、原查询/公式/分摊/导出、目录/Mapping、动态实体列、调度/事件。API沿现有Schema与VCUDE；无权403、参数/配置按既有400/409/422、资源404、有权空结果200。
- 不以测试数、合成结果、部署完成冒充生产业务验收；每轮可独立提交、审批发布，不把所有小卡攒成一次大上线。
- 当前主线已调整为前置B基础；B00.a已完成只读调查与冻结准备合同，Person/Employment首版定义、工作地enum归Person及标识字段string口径已确认；B01.a定义/归属子项已开发验收通过；真实来源接管、时间轴实现和期间结果服务按后续卡执行。

### 1.1 需求、任务与证据规则

1. 开工按README协议选定唯一卡，在§9写一条“进行中”记录，引用§4对应FR和AC；多次重复模板使用R09.a/B03.a等实例编号，写清本次唯一形态/约束，不能一次执行整个模板。
2. §4的FR映射为本卡重点，不取消相关依赖中的其他安全需求。所有卡同时遵守FR-G01–FR-G04；FR-A02/FR-A07或FR-B04/FR-B05等基础安全从首个相关业务卡生效，不因未排到另一张卡延后。
3. 卡片状态仅使用：待核查、待整合、待开发、进行中、开发验收通过、生产待验收、完成、阻塞、不适用。已有能力的“待整合”不是重写许可；未复现或现有实现已满足时，可用可复核证据关闭本卡本次范围，不强改代码。
4. 每条完成证据写需求/AC编号、代码位置或现有入口、实际命令/操作与结果、未运行项、对象/身份/配置范围和停止方式。FR完整验收须累积其全部适用证据；一个MVP局部通过不把整条FR或原父任务自动标完。
5. 开发验收只称开发验收。没有生产条件时保持“生产待验收/阻塞”；准备卡/纯本地清理可在明确不适用原因后完成，不强加无关生产门槛。取消路线不标为“实现完成”，其已有代码按R13逐引用退役。
6. 不自行新建planning/report文件、增加第二份任务表或更改FR含义。范围需变化先改spec并得到业务确认，再改映射；已确认整合方向下的实现选择由代码核对决定。
7. 每个开发MVP在§3.1以独立`- [ ]`项显示。仅当该项列明的成功/拒绝验收完成、证据已写入§4状态及§9证据账后才改为`- [x]`；只完成代码、仅测试通过但所需PC/真库/API未通过，均不得勾选。准备卡仅在只读核查结果与停止条件记录齐全后勾选。任务状态与勾选须在同一次文档更新中同步；遇阻维持未勾选并写明阻塞，不代表其他独立卡必须等待。
8. 复选框只表达该MVP交付合同是否通过，不代表FR、父任务、生产部署或生产验收整体完成；这些仍按§4/§9各自状态记录。

R08的分摊内部依赖只能服务获准分摊结果，独立工资/奖金输出仍独立授权；缺授权表达只补该用途的声明，不新建计算平台。R09每轮不超过一个独立关系/计算形态。R16随每次实际生产发布执行，不等R13或全部A完成。

#### 初始化前必须承接的调查发现

1. **同日粒度缺口**：本地PK工号+生效日期无序号；旧同步[同PK取最后一条](../../hr-portal/backend/app/datasources/sync_service.py#L737)。新时间轴须核准来源事件键/可靠同日顺序或获准local事件分配；迟到不按接收时间猜业务顺序，不能从已覆盖快照还原历史，本次不改旧PK。
2. **稳定身份未因工号存在而解决**：未发现自然人/雇佣源记录键；证件号码存在也不授权按证件自动合并。Person/Employment定义可先设计，但真实接管必须有核准来源身份关系。保持工号业务含义，不把employee_no重命名为内部人员ID。
3. **类型和值域不是同名直绑**：复用工号标准ID4/string，补源numeric转换证据；工作地源string→标准enum须核准选项/未知值/停用值规则，不从员工值自动推断。手机号/卡号数值化风险单独受控处理，不恢复猜测前导零；薪酬约定string→金额及单位/币种不直接强转。
4. **相似列独立保留**：full_name/chinese_name有不同列UUID；employee_status/employment_status、terminated_date/expected_departure_date、position_level/management_level、position/standard_position不能自动合并。现[花名册合同](../../hr-portal/backend/app/data/employee_roster_contract.py)优先将预离职映射departure_date、把岗位层级显示为职级，初始标准定义需澄清，但不得顺带改变绩效快照/原报表。组合展示字段job_family_category_title_grade不先生成第二字段字典。
5. **薪酬约定不等于月度工资结果**：base_salary说明为固定基本薪酬，position_salary为岗位工资，target_year_end_bonus为目标值；具体归属暂列薪酬约定候选，不把它们机械放入Person普通基本信息，也不当作已发生月度事实。月度结果按真实期间/项目/批次独立保存，不能取最大生效序号吞掉同月项目。
6. **保护先核准**：本地证件/手机/卡号/岗位工资等缺已查敏感分类证据；人员候选/HRBP/上级仍是string不能按姓名转稳定关系。初始化必须先确认实体资源权、人员D与字段分类，普通配置管理员不因创建Person定义而拥有全部人员读写，本次不配权/改scope_role/补分类。
7. **时间属性不能误用现有标志**：StandardField.has_history现用于迁移前字段定义/审批证据保全，不是人员字段值时间轴开关；RegisteredTable.is_period是期间表配置，不是通用有效期。新生效日期/序号属于业务记录模型，不把旧标志改义，不重建字段语义版本。
8. **首版卡片与写者须衔接**：Person/Employment首版定义已确认，工作地enum归Person；原B01.b的获准local记录合同不自动成为真实Person/Employment写权限，需按隔离合成样例/服务写者分别冻结。内置Person/Employment通过不替代FR-B01非内置通用扩展验收，后者保留后续实例，不用工作地实体或假人员交差。
